# Master-data audit evidence

## Ownership and event flow

Master Data owns `master_data_audit_events` and the `master_data_change_requests` lifecycle. The API verifies JWT identity before installing a scoped actor for the synchronous use case. Direct create, update and deactivate operations stamp the authenticated actor on the affected row and append an event with the persisted before/after row IDs. The event and row save share the service transaction; an audit insert failure rolls back the command. The actor scope is cleared after the servlet call. Internal Closing fiscal-period writes keep the separately verified `closing` service and signed business actor, and append `FISCAL_PERIOD_STATUS` with prior/new status and the persisted period ID.

For controlled changes, `reason` remains the original request rationale; `decision_reason` holds a rejection rationale. REQUESTED, APPROVED, REJECTED and APPLIED events retain time, actor, target key, request ID and optional `source_reference`. Their event `reason` field is a bounded `request:sha256:...` or `decision:sha256:...` reference to the corresponding request record, never the free text. The APPLIED event joins the request to the previous/resulting SCD2 row IDs; DEACTIVATE uses the same ID on both sides. An HTTP apply records the verified executor; scheduled apply records `master-data-scheduler` and the approving business actor. The request row retains the requester and approver. Event records contain identifiers and digest references only; they do not copy `payload_json`, registration numbers, account data or credentials. A reason is user-supplied text and must not be used to submit secrets.

## Retention, export and integrity

There is no application delete or purge path for these events. Operations owns backup, access control and export; retain committed evidence for at least seven years pending the organization's approved schedule. Retention expiry requires a reviewed policy and forward migration, never an application cleanup of unexported rows. `JpaMasterDataAuditAdapter.exportAfterId(lastId, pageSize)` exports at most 1,000 ordered events per page and verifies each SHA-256 fingerprint, including the sequence-assigned export ID, before returning it. A caller must store the last exported ID, page until empty, reconcile counts and highest IDs with the source, and write the exported pages to independently controlled immutable storage. SHA-256 detects accidental row or ordering-ID changes but is not a keyed signature: a DB administrator could rewrite both an event and its hash. An independent immutable export, restricted DB update/delete grants, backups and restore drills are required for adversarial integrity and disaster recovery. External log retention was not inspected or assumed.

The synthetic embedded PostgreSQL `MasterDataAuditEmbeddedPostgresqlTest` migrates V1→V11, validates JPA mapping, appends under a role with SELECT/INSERT plus sequence access and no UPDATE grant, exports committed evidence and detects tampering. H2 tests exercise shared transaction rollback, paging, retained rows and changed row/ordering IDs. These tests do not prove production grants, external storage durability or restore behavior.

Run the synthetic evidence locally with `./gradlew :master-data:core:test --tests '*JpaMasterDataAuditAdapterTest' :master-data:api:test --tests '*MasterDataAuditEmbeddedPostgresqlTest' --offline --no-daemon --console=plain --max-workers=2`. It uses generated fixtures and an isolated embedded server; no operational database URL is read.

Before promotion, operations should inspect actual PostgreSQL grants on `master_data_audit_events`; the application DB role should receive table `SELECT` and `INSERT` plus `USAGE` on `master_data_audit_event_ids`, without table `UPDATE`, `DELETE` or `TRUNCATE`. Export should use a dedicated reader role. Capture evidence of a page export, count/high-watermark reconciliation, hash verification, restore drill and configured immutable-store retention. A synthetic database test supplies development evidence only; the production grants and retention controls require operations sign-off.

## Recovery

Revert application code through a reviewed PR. Preserve committed audit rows and correct schema with a forward migration. If export verification fails, stop export at the last verified ID, isolate the database snapshot and investigate; do not recompute hashes in place. Failed business commands roll back their matching event in the same transaction.
