# K-Bank 차세대 재무 시스템 - E2E 비즈니스 워크플로우

## 2.1 공통 파이프라인 (Common Pipeline)

*   **수집 (Collection):** 다양한 원천 시스템(ERP, Banking 시스템, 수기 입력 등)에서 발생한 거래 데이터를 수집.
*   **표준화 (Standardization):** 수집된 데이터를 재무 시스템 내부의 표준화된 형식으로 변환. (예: 계정 코드 매핑, 통화 변환, 일자 형식 통일)
*   **분개 (Journalizing):** 표준화된 데이터를 기반으로 복식 부기 원칙에 따라 차변/대변 계정 및 금액을 결정하여 분개 생성. (룰 엔진 활용)
*   **전표 (Journal Entry):** 생성된 분개를 묶어 하나의 전표(Journal Entry)로 확정. 전표 번호 부여 및 상태 관리(DRAFT, APPROVED, POSTED 등).
*   **전기 (Posting):** 확정된 전표를 총계정원장(GL) 및 보조원장(SL)에 반영하여 계정 잔액 및 거래 내역 업데이트.

## 2.2 ERP 스트림: 대표 시나리오 (예시: P2P/AP - 구매대금 지급)

```bpmn
설명: 구매 요청부터 대금 지급까지의 ERP P2P/AP 프로세스
시작 이벤트: [ERP] 구매 요청 발생
수영장: ERP팀
  활동: 구매 오더 생성
  게이트웨이(병렬): [예산 초과 여부 확인]
    경로1: 예산 초과
      활동: 예산 승인 요청 (수동)
      게이트웨이(배타적): [예산 승인 여부]
        경로1: 승인됨
          활동: 구매 오더 진행
        경로2: 거부됨
          활동: 구매 오더 취소
          종료 이벤트: 구매 요청 종료 (예산 거부)
    경로2: 예산 승인됨 (또는 초과 안됨)
      활동: 입고 확인 및 검수
      활동: 공급업체 인보이스 수신
수영장: FI팀
  활동: 인보이스 표준화 및 전표 생성 룰 적용
  게이트웨이(배타적): [전표 생성 룰 결과]
    경로1: 전표 생성 룰 정상 적용
      활동: AP 전표(부채) 생성 (차변: 비용 계정, 대변: 미지급금)
      게이트웨이(병렬): [결제 승인 필요 여부]
        경로1: 승인 필요
          활동: 결제 승인 요청 (이중 승인 원칙 적용)
          게이트웨이(배타적): [결제 승인 여부]
            경로1: 승인됨
              활동: 지급 대상 확정
            경로2: 거부됨
              활동: 지급 보류 (오류큐/재처리 대상)
              활동: 오류큐에 지급 보류 내역 등록
              활동: 재처리 대기
              종료 이벤트: 구매 요청 종료 (지급 보류)
        경로2: 승인 불필요
          활동: 지급 대상 확정
    경로2: 전표 생성 룰 오류
      활동: 오류큐에 전표 오류 내역 등록
      활동: 재처리 대기
      종료 이벤트: 구매 요청 종료 (전표 오류)
수영장: 자금팀
  활동: 지급 실행 (은행 시스템 연동)
  게이트웨이(배타적): [지급 결과]
    경로1: 지급 성공
      활동: 지급 전표 생성 (차변: 미지급금, 대변: 현금/예금)
      종료 이벤트: 구매 요청 완료 (대금 지급 완료)
    경로2: 지급 실패
      활동: 오류큐에 지급 실패 내역 등록
      활동: 재처리 대기
      종료 이벤트: 구매 요청 종료 (지급 실패)
```

## 2.3 Banking 스트림: 대표 시나리오 (예시: Loans - 대출 실행)

```bpmn
설명: 고객 대출 실행 및 회계 처리 프로세스
시작 이벤트: [Banking System] 고객 대출 실행 요청
수영장: 여신팀 (대출 관리 시스템)
  활동: 대출 계약 정보 확인
  게이트웨이(배타적): [대출 승인 여부]
    경로1: 승인됨
      활동: 대출 원금 실행 (고객 계좌 입금)
      활동: 이연대출부대손익 항목 생성
    경로2: 거부됨
      활동: 대출 요청 거부 알림
      종료 이벤트: 대출 실행 종료 (거부)
수영장: FI팀
  활동: 대출 실행에 따른 회계 분개 룰 적용
  게이트웨이(배타적): [전표 생성 룰 결과]
    경로1: 전표 생성 룰 정상 적용
      활동: 대출채권 전표 생성 (차변: 대출채권, 대변: 이연대출부대손익, 현금/예금)
      활동: 이연대출부대손익 상각 스케줄 생성
      종료 이벤트: 대출 실행 완료 (회계 처리 완료)
    경로2: 전표 생성 룰 오류
      활동: 오류큐에 전표 오류 내역 등록
      활동: 재처리 대기
      종료 이벤트: 대출 실행 종료 (전표 오류)
```

## 2.4 공통 운영 (Common Operations)

### 2.4.1 오류큐 (Error Queue)
*   **정의:** 자동화된 프로세스에서 발생하는 오류를 기록하고 관리하는 시스템. 수동 개입 및 재처리 대상.
*   **운영 방안:** 오류 발생 시 오류 유형, 발생 시간, 관련 거래 정보 등을 상세히 기록. 운영 담당자에게 알림 및 오류 처리 대시보드 제공.

### 2.4.2 재처리 (Reprocessing)
*   **정의:** 오류큐에 적재된 오류 건에 대해 원인을 분석하고, 수정 후 다시 시스템에 처리하도록 하는 과정.
*   **운영 방안:** 재처리 정책 (`docs/principles_and_policies.md` 참조)에 따라 재처리 실행. 중복 처리 방지 및 멱등성 보장. 재처리 이력 관리.

### 2.4.3 대사 (Reconciliation)
*   **정의:** 서로 다른 시스템 또는 데이터 소스 간의 데이터 일치 여부를 확인하는 과정. 재무 데이터의 정합성 확보.
*   **운영 방안:** 원천-회계 대사, 계정 대사, 은행 계좌 대사 등 주기적인 대사 프로세스 운영. 차이 발생 시 원인 분석 및 조정 전표 처리.

### 2.4.4 마감 (Closing)
*   **정의:** 특정 회계 기간의 거래를 확정하고, 해당 기간의 재무제표를 생성하기 위해 모든 회계 처리를 완료하는 과정.
*   **운영 방안:** 마감 캘린더, 체크리스트, 게이트 관리. 기간 잠금 및 재오픈 승인 절차. 결산 평가 및 조정 배치 실행.

## 2.5 스윔레인 표준 (Swimlane Standard)

*   **원천 (ERP/상품):** 거래 발생의 시작점. ERP 시스템 또는 Banking 상품 시스템.
*   **FI (재무회계):** 회계 처리 및 전표 생성, 원장 관리.
*   **세무 (Tax):** 세무 관련 회계 처리 및 보고.
*   **자금 (Treasury):** 자금 집행 및 관리.
*   **운영 (Operations):** 시스템 운영, 오류 처리, 재처리.
*   **감사 (Audit):** 프로세스 및 데이터의 적정성 검토.

## 2.6 게이트웨이 표준 (Gateway Standard)

*   **예산초과:** 예산 집행 가능 여부 확인.
*   **세무대상:** 세무 관련 처리가 필요한 거래 여부 확인.
*   **자산·리스:** 고정자산 또는 리스 관련 거래 여부 확인.
*   **마감잠금:** 해당 기간에 대한 데이터 변경 가능 여부 확인.
*   **승인필요:** 추가적인 승인 절차가 필요한지 확인.

## 2.7 예외 처리 (Exception Handling)

*   **취소 (Cancellation):** 이미 발생한 거래를 무효화.
*   **환불 (Refund):** 지급된 금액을 되돌려 받는 처리.
*   **역분개 (Reversal):** 원본 전표의 차변/대변을 반대로 기표하여 취소.
*   **지연 수신 (Delayed Receipt):** 원천 데이터가 정해진 시간 내에 수신되지 않음.
*   **중복 수신 (Duplicate Receipt):** 동일한 원천 데이터가 여러 번 수신됨.
