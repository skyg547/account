# 모던 재무 시스템 초보자 가이드

이 문서는 처음 합류한 개발자와 업무 담당자가
"무엇을 먼저 읽고, 어떤 순서로 변경하고, 어떻게 검증할지"를 빠르게 이해하도록 만든 입문 가이드입니다.

## 1. 이 저장소를 한눈에 이해하기

이 프로젝트는 회계/재무 업무를 모듈 단위로 분리한 멀티모듈 시스템입니다.

핵심 원칙:

- 헥사고날 아키텍처(Port/Adapter) 준수
- 도메인 규칙은 `domain`에, 유즈케이스 조합은 `application/service`에 배치
- 외부 기술(JPA, API, 메시징)은 `adapter` 또는 `infrastructure`로 격리
- 대용량 배치 모듈은 오케스트레이션 중심으로 유지

## 2. 모듈을 읽는 기본 순서

아무 모듈이든 아래 순서로 보면 이해 속도가 가장 빠릅니다.

1. `README.md`
2. `docs/beginner-guide.md`
3. `docs/process-flow.md`
4. `docs/schema.md`
5. 코드: `domain -> application/port -> application/service -> adapter`

예시:

- `tax/docs/*`: 매입 세금계산서 검증/조회
- `expenditure-resolution/docs/*`: 지출결의 승인/예산/지급
- `governance/docs/*`: 내부회계 통제와 결산 통제 정책

## 3. 업무 초보자가 먼저 알아야 할 회계 관점

- "증빙"(세금계산서, 계약, 결의서)은 후속 회계 처리의 근거입니다.
- 금액 검증(`BigDecimal`)은 단순 수학이 아니라 회계 정합성 통제입니다.
- 상태값(`DRAFT`, `APPROVED` 등)은 업무 절차의 승인 이력입니다.
- 예산 통제는 승인 절차와 함께 내부회계 통제의 핵심입니다.

## 4. 개발 초보자 작업 순서

1. 변경하려는 모듈의 `README`와 `docs`를 먼저 읽습니다.
2. API 변경이면 `Controller -> DTO -> Service -> Test` 영향 범위를 함께 확인합니다.
3. 배치 변경이면 파라미터, 재실행 가능성, 정합성 검증 포인트를 먼저 정리합니다.
4. 코드 수정 후 모듈 단위 빌드/테스트를 먼저 실행합니다.
5. 문서(`README`, `docs/*.md`)를 코드와 동시에 갱신합니다.

## 5. 최소 실행/검증 명령

```bash
./gradlew projects --console=plain
./gradlew :tax:build --console=plain
./gradlew :expenditure-resolution:build --console=plain
./gradlew :governance:test --console=plain
```

프로젝트 상황에 따라 특정 모듈만 우선 검증해도 됩니다.

## 6. 문서 품질 점검 기준

- 깨진 문자(인코딩 문제)가 없어야 함
- 경로 링크가 실제 파일과 일치해야 함
- 클래스/패키지 리팩터링 시 문서 경로 즉시 갱신
- 초보자가 읽어도 "왜 필요한 규칙인지"가 설명되어야 함

## 7. 변경 전 체크리스트

- 변경 범위가 요청 범위를 벗어나지 않았는가?
- 비즈니스 규칙이 도메인/서비스 경계에 맞게 위치하는가?
- 단순 위임 코드만 늘리지는 않았는가?
- 문서와 코드가 서로 다른 설명을 하고 있지 않은가?

## 8. 변경 후 체크리스트

- 관련 테스트 또는 최소 빌드를 실행했는가?
- 실행하지 못했다면 이유를 남겼는가?
- 남은 리스크(예: 통합 어댑터 미구현, 운영 정책 미확정)를 기록했는가?

이 가이드를 기준으로 작업하면, 신규 인원도 같은 품질 기준으로 빠르게 협업할 수 있습니다.
