# [auth] End JWT privileges when individual approved role assignments expire

Audit ID: **F03**; baseline `a97d10ab6efc2570a88f83d630242cd748f8be57`; suggested priority **P1**.

Labels: `area:core`, `type:bug`, `priority:p1`

## Problem and code references

JWT expiry uses a fixed TTL and embedded assignments omit validity windows. Token-version validation only requires an unchanged roleVersion and any currently effective role. A permanent basic role therefore keeps a token valid after an elevated role in the same token expires.

## Architectural / business impact

Time-limited privileged access can remain usable until token expiry, beyond its approval window.

## Proposed solution

Cap token lifetime at the earliest included authorization expiry, or validate and project current assignments on every request. Define exact expiry and clock-skew behavior. Do not assume a roleVersion changes merely because time passes.

## Acceptance criteria

- [ ] With permanent USER plus temporary ADMIN, elevated access fails at validTo even while USER remains effective.
- [ ] Clock-controlled issuer/version/gateway tests cover before, exactly at and after expiry, including cached validation.
- [ ] Newly effective grants and refresh behavior are explicitly defined without silently extending old privileges.

## Evidence and limits

Synthetic actual issuer plus actual AuthService validation reproduced the defect with a controlled validation clock; generated signing material/token remained in memory and was not printed.
