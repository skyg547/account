# [auth] Bind PAT management to authenticated ownership and administrator authority

Audit ID: **F01**; baseline `a97d10ab6efc2570a88f83d630242cd748f8be57`; suggested priority **P1**.

Labels: `area:api`, `type:bug`, `priority:p1`

## Problem and code references

PAT creation accepts a caller-selected username and defaults to admin. Listing and revocation accept a supplied owner; administrator listing has no authorization and force-revoke passes isAdmin=true. The service trusts these inputs and uses case-insensitive owner comparison even though user identities are stored as distinct keys.

## Architectural / business impact

A caller reaching the auth service can anonymously create token records for arbitrary users, list token metadata, and revoke tokens. This is an authorization defect independently of whether PAT authentication is implemented. Current gateway routes do not expose PAT endpoints; public-gateway exploitation and downstream PAT impersonation are not claimed.

## Proposed solution

Derive identity and privileges from a verified principal, remove admin defaults and caller-controlled administrator flags, and enforce canonical ownership in an inbound PAT use case. Add actor-attributed creation/revocation events.

## Acceptance criteria

- [ ] Anonymous callers cannot create/list/revoke PATs; ordinary users cannot act for another identity or invoke administrator actions.
- [ ] Use the same canonical identity semantics as AuthUser; case variants must not authorize another account.
- [ ] Full HTTP tests include spoofed body/query identities, forged headers, owner success and verified administrator success. Secure the boundary before adding gateway routes.

## Evidence and limits

Reproduced with actual controller and mocked service in standalone MockMvc: anonymous administrator list=200, revoke=204, empty create delegates owner=admin. No real token or user accessed.
