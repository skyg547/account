# [master-data] Fail closed on duplicate business-partner results in bulk reference queries

Audit ID: **F10**; baseline `a97d10ab6efc2570a88f83d630242cd748f8be57`; suggested priority **P2**.

Labels: `area:core`, `type:bug`, `priority:p2`

## Problem and code references

The bulk adapter collects duplicate codes using (a,b)->a. Unlike singular Optional queries, it silently suppresses overlapping active versions. Repository order normally makes this the oldest overlapping validFrom; equal-date order is unspecified.

## Architectural / business impact

Batch consumers can receive a plausible but incorrect partner name/type/status while data corruption is hidden. F07 prevents new overlaps but does not make legacy/imported corrupt data safe to read.

## Proposed solution

Detect duplicates and raise a typed integrity error, or return an explicit per-key failure under a documented bulk contract. Never pick a version silently.

## Acceptance criteria

- [ ] Two active versions of one requested key cause a deterministic error with no successful substitute value.
- [ ] Test equal and unequal start dates, repeated input codes, normal distinct keys and empty input.
- [ ] Consumers cannot treat partial/corrupt reference data as a successful financial validation.

## Evidence and limits

Actual adapter probe returned one entry (first partner) for two same-code results.
