# [master-data] Reject sequential duplicate future-dated CREATE intervals

Audit ID: **F08**; baseline `a97d10ab6efc2570a88f83d630242cd748f8be57`; suggested priority **P1**.

Labels: `area:core`, `type:financial`, `priority:p1`

## Problem and code references

Direct/core CREATE checks only whether a row is active today. The first future-dated creation is invisible to that check, so a second identical future interval is accepted. The same pattern exists for all four supported masters, including BusinessPartner whose existsByBusinessPartnerCode default checks today.

## Architectural / business impact

A single administrator can create overlapping scheduled master rows through ordinary sequential calls; no race or special database failure is required.

## Proposed solution

Define CREATE as new business-key creation, or explicitly permit disjoint reactivation with an interval-overlap query. Apply that policy consistently to all entrypoints and back it with F07 constraints.

## Acceptance criteria

- [ ] Two sequential future CREATE requests with the same key/overlapping dates reject the second and preserve the first.
- [ ] Cover all four types, historical overlap, inclusive adjacent dates and legitimate nonoverlap policy.
- [ ] Direct/core entrypoints and approved flows use consistent semantics; approved CREATE already has a history-count guard and must retain it.

## Evidence and limits

Actual ProductService reproduced two accepted identical future intervals with a date-aware in-memory port. Other three paths source-confirmed; this probe did not execute their database adapters.

Related history: #667 concerns repeated future UPDATE, so this is a separate CREATE defect.
