## Problem statement

Settlement loads and modifies cumulative amounts without a version or exclusive lock. Durable reference replay protection handles sequential retries but does not serialize different references against the same open item.

## Reproduction / evidence

Static schedule: both transactions load remaining100; one settles40/refA, another50/refB. Each validates against100 and writes its own absolute totals. Depending on collection persistence and commit order, monetary/reference state can lose an update or diverge. No PostgreSQL concurrency experiment was executed.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

The GL-owned open-item view can disagree with actual receipts/payments and allow over-settlement across concurrent transactions.

## Proposed solution

Serialize settlement per item or use a versioned atomic ledger of settlement effects with retry and durable idempotency.
