## Problem statement

Beginning balances are copied only when a daily row is first created. Posting on an earlier date changes that row but does not propagate or invalidate later projections.

## Reproduction / evidence

P09: day1 debit100, day2 debit20, then another day1 debit10; day1 becomes110 but day2 remains120 instead of130. This executes the actual service against a stateful port double. Documentation acknowledges that operators must manually rebuild all later dates; no enforced repair/invalidation accompanies posting.

Executed diagnostic observations: `P09` in [probe-results.json](../evidence/probe-results.json); source: [AuditProbes.java](../evidence/AuditProbes.java). Probe PASS confirms the observation, not remediation.

## Financial / architectural impact

Subsequent-date inquiries and closing consumers can use stale balances despite successful posting.

## Proposed solution

Propagate historical deltas or durably invalidate/rebuild all affected future projections before treating them as authoritative; alternatively reject unsupported backdating.

## Acceptance criteria

- [ ] Test cross-month/year historical postings for GL and all SL dimensions.
- [ ] Queries cannot silently expose a stale authoritative ending balance while repair is pending.
- [ ] Rebuild ranges include every affected successor date, with posting/rebuild concurrency control.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

Period aggregation tests cover summation order, but not backdated propagation.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
