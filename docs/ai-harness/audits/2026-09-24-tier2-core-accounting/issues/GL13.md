## Problem statement

Cleanup commits deletion of live GL/SL balances before independent chunk commits rebuild them from a live POSTED source. There is no source watermark, publication generation or posting/read exclusion protocol.

## Reproduction / evidence

Static reproduction plan: fail the first writer after cleanup, or after one chunk of more than100 details; live balances are absent/partial. A journal posted after cleanup can update balances online and later be read again by rebuild, counting twice. No full job fault/concurrency test was executed in this audit.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

Reporting and closing can observe incomplete or duplicated balances during failure or overlap.

## Proposed solution

Build a separate generation from a stable source snapshot and publish atomically, or implement an explicit posting/read barrier and reconciliation gate before release.

## Acceptance criteria

- [ ] Fault injection after cleanup and at multiple chunk boundaries never exposes accepted partial financial results.
- [ ] Same-instance restart, overlapping ranges and concurrent posting reconcile exactly to journals.
- [ ] Do not simply rerun cleanup while resuming a saved reader offset; checkpoint and output generation must agree.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

The job behavior test uses two lines and a fresh timestamp JobInstance, not a multi-chunk failure/restart.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
