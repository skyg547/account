## Problem statement

Each valuation/provision API request commits a fresh run ID. That ID becomes new lineage, so retrying the same business request creates a distinct draft. Journal success followed by execution-record failure can also leave an orphan draft behind a FAILED run.

## Reproduction / evidence

Static schedule: repeat the same period/type request after response loss, or fail recorder completion after draft creation. NOT_SUPPORTED orchestration and REQUIRES_NEW recorder phases cannot roll back the already-created journal.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

Duplicate drafts can later be approved and double count adjustments; run status does not reliably describe outstanding financial effects.

## Proposed solution

Accept a stable execution key with unique storage and resumable phase tracking, and reconcile journal outcome after ambiguous failures.

## Acceptance criteria

- [ ] Equivalent retries return the original run and draft; changed content under the same key fails.
- [ ] Faults after draft creation recover the existing journal rather than allocate another run.
- [ ] Run failure/success evidence exposes orphan or pending financial effects accurately.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

Existing tests do not simulate duplicate HTTP requests or journal-success/recorder-failure recovery.

The six requested module suites passed 369 tests, but their success does not establish this missing control.
