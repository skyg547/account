## Problem statement

Lock and pending-reopen checks are check-then-insert without unique active/pending constraints. Period lock indexes are nonunique, yet lookup expects one Optional result.

## Reproduction / evidence

Static schedule: two callers both see no lock and insert one each; subsequent findByFiscalPeriodId can fail on multiple rows. The same pattern permits multiple PENDING reopen approvals.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

Period controls can become ambiguous or operationally unavailable, and approvals can compete for one reopening.

## Proposed solution

Enforce uniqueness of active locks and pending approvals at the database boundary, with serialized creation and explicit conflict mapping.

## Acceptance criteria

- [ ] Two concurrent requests create at most one active lock/pending approval per period.
- [ ] Existing duplicate migration/repair policy is explicit before adding constraints.
- [ ] Unlock/decision preserves immutable history and does not leave ambiguous active rows.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.
