## Problem statement

Public setters and add/remove/clear/setDetails do not check status. List.copyOf protects collection structure only; elements remain mutable. JPA callbacks update timestamps but do not enforce historical immutability.

## Reproduction / evidence

P03 changes a POSTED accounting date and line amount, then clears its details in memory without rejection. JPA field mappings allow dirty updates; no posted-state database guard was found. No update/delete HTTP route is claimed. Existing GL/SL detail FKs can block deletion of referenced lines, so successful orphan deletion was not established.

Executed diagnostic observations: `P03` in [probe-results.json](../evidence/probe-results.json); source: [AuditProbes.java](../evidence/AuditProbes.java). Probe PASS confirms the observation, not remediation.

## Financial / architectural impact

A managed-entity caller can change historical financial facts after the immutable posting snapshot and stored GL/SL entries were produced, breaking journal-to-ledger reconciliation.

## Proposed solution

Enforce state-aware aggregate mutations and immutable posted line/header values; route corrections through linked reversal/adjustment commands and add persistence-level protection for financial columns.

## Acceptance criteria

- [ ] Posted financial headers, line amounts/sides/accounts/dimensions and collection membership reject mutation.
- [ ] Flush/clear JPA tests prove committed posted data cannot be changed or deleted through repository/cascade paths.
- [ ] Allow only explicitly controlled nonfinancial audit annotations, if required, without rewriting accounting history.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

Domain and immutable snapshot tests do not exercise managed POSTED dirty checking, orphan removal or repository deletion.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
