## Problem statement

General closing commands accept user/requestedBy/approvedBy from query/body fields without binding them to trusted caller identity or enforcing closing permissions. Reopen separation of duties compares only those supplied strings.

## Reproduction / evidence

Static reproduction: one authenticated caller requests reopening as USER_A and approves as USER_B_MANAGER. The body names satisfy domain inequality even though the real principal is unchanged. The controller boundary test accepts body identity with a mocked use case. EOD has a stronger trusted-header/role boundary and is not included in this accusation.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

A single user can authorize their own period reopening or issue privileged close/lock commands under another recorded name.

## Proposed solution

Adopt trusted-principal binding and command-level roles for all financial control routes, retaining distinct requester/approver principals.

## Acceptance criteria

- [ ] One principal cannot request and approve reopening by changing body identities.
- [ ] Unauthorized/missing roles reject close, lock, reopen, valuation/provision and annual-close commands.
- [ ] Test Gateway-context-to-real-use-case flows; preserve EOD's existing role checks.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

Current general-controller tests mock the use case and do not prove authenticated SoD.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
