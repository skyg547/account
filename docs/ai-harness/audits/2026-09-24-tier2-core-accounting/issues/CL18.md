## Problem statement

HTTP approveAndPost always issues approve then post. On restart, the adjustment adapter can reuse an APPROVED/POSTED journal, but repeated approval is illegal. The local JournalPostingAdapter has status-aware behavior that the HTTP implementation lacks.

## Reproduction / evidence

Static failure sequence: approval commits, posting fails before commit, same job restarts; repeated approval fails because the journal is already APPROVED. After a lost successful posting response, an unconditional repeat can similarly fail on POSTED.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

Remote closing jobs can become stuck despite a recoverable journal state, leaving approvals or postings ambiguous to operators.

## Proposed solution

Read and validate authoritative journal status/content and resume the next needed phase; keep retries idempotent across response loss.

## Acceptance criteria

- [ ] APPROVED resumes posting without reapproval; POSTED verifies and returns success.
- [ ] Test response loss after create, approve and post for FX/ECL auto-post.
- [ ] Rejected/incompatible journals fail clearly; no blind mutation retries.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

HTTP tests cover error propagation, not multi-phase recovery.
