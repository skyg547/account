## Problem statement

The source includes only non-reporting-currency journals, while FX adjustment commands use reporting currency. Prior posted valuation adjustments never enter the carrying value used for the next valuation.

## Reproduction / evidence

P12 runs the actual source SQL on synthetic H2 rows: USD100/base1000 plus an already-posted KRW200 valuation. Reader still returns base1000; at unchanged rate12 the service generates another200. Correct second adjustment is zero.

Executed diagnostic observations: `P12` in [probe-results.json](../evidence/probe-results.json); source: [AuditProbes.java](../evidence/AuditProbes.java). Probe PASS confirms the observation, not remediation.

## Financial / architectural impact

Repeated valuations overstate assets/income or liabilities/losses cumulatively, despite deterministic idempotency within one batch identity.

## Proposed solution

Retain source-currency attribution for base-only adjustments and include all effective prior valuations in carrying value without changing foreign principal.

## Acceptance criteria

- [ ] Unchanged-rate subsequent months produce zero after the prior adjustment is posted.
- [ ] Cover rising/falling rates, liability/abnormal signs and multiple source currencies on one account.
- [ ] Reconcile book value to posted journals and preserve valuation/reversal lineage.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

Existing FX tests cover a single isolated valuation, not successive posted valuations.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
