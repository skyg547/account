## Problem statement

Posting reads APPROVED without an exclusive lock, version or compare-and-set claim. Ledger entry detail references are nonunique, so two transactions can both validate and insert the same accounting movements.

## Reproduction / evidence

Static concurrency schedule: transactions A/B both fetch the same APPROVED journal; both construct valid snapshots, mark POSTED and persist GL/SL rows. Existing balance rows prevent a new-key constraint failure from masking the duplicate-entry path. This interleaving was not executed against PostgreSQL.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

One economic event can appear twice in GL/SL, even though sequential duplicate posting correctly fails.

## Proposed solution

Atomically claim the journal for posting and enforce a unique durable posting identity in the database; return a deterministic result for safe retries.

## Acceptance criteria

- [ ] Two independent connections posting the same ID produce exactly one set of ledger entries.
- [ ] Test both JPA and JDBC paths and failure after claim/before entry insert.
- [ ] A repeated completed request is a documented no-op/result or conflict, never an additional financial effect.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.
