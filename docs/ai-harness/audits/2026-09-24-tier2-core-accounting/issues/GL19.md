## Problem statement

Financial domain packages contain JPA mappings, lifecycle callbacks, a JPA converter and Spring Data repositories. Outbound application ports have improved service isolation, but the requested framework-free domain boundary is not met.

## Reproduction / evidence

Static imports show entity/repository framework dependencies; across both audited domain trees 30 of42 Java files import Spring or JPA. GeneralLedger, Debit/Credit and AccountingPrecision are positive examples of framework-independent financial types.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

Persistence lifecycle and repository APIs remain coupled to domain rules, making immutable aggregate enforcement and isolated financial testing harder.

## Proposed solution

Incrementally move Spring Data repositories and JPA mappings into infrastructure, with explicit domain mapping and architecture dependency checks.

## Acceptance criteria

- [ ] Domain compiles/tests without Spring/JPA imports.
- [ ] Preserve aggregate ownership, precision, transaction behavior and existing persistence mapping tests during extraction.
- [ ] No repository save/delete API is exposed as a domain service contract.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

No executable domain-dependency architecture guard found; scope the migration separately from urgent financial fixes.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
