## Problem statement

The API run paths read AutomatedJournalRule.amount and generate a fixed KRW draft. They do not invoke the real FX/ECL calculation services or inspect exposures, rates, finalized summaries and existing allowances.

## Reproduction / evidence

Static reproduction: configure amount100, invoke a provision run with type ECL and no finalized ECL summary. The path builds the configured100 adjustment. Existing tests intentionally assert configured-rule amounts; real Spring Batch ECL/FX services are separate paths.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

Users can receive a successful run response and a valuation/provision draft unsupported by the underlying financial calculation. The returned run status is PENDING_APPROVAL, not COMPLETED. Default DRAFT review limits immediate posting impact but does not establish correctness.

## Proposed solution

Route financial run commands to the validated calculation use cases, or expose fixed entries as an explicitly manual adjustment feature with different semantics.

## Acceptance criteria

- [ ] API and batch calculations use the same financial policy and required source evidence.
- [ ] Missing FX rates/ECL summaries fails the financial run before journal creation.
- [ ] Any retained manual fixed-amount workflow is clearly named, authorized and separately audited.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

Current API/service tests certify fixed-amount behavior rather than parity with real calculation services.

No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
