## Problem statement

Manual/event creation always saves a new journal. The contract adapter only performs a check-then-create lookup on lineage, with no unique request key; it returns the first existing journal without comparing financial content. Kafka bypasses even that check.

## Reproduction / evidence

Static scenarios: repeat an event or manual request after a lost response; race two contract requests with the same lineage; reuse lineage with a changed amount. These produce duplicates or return an unrelated earlier result, depending on path.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

At-least-once delivery and client retries can duplicate financial activity or falsely acknowledge a changed request.

## Proposed solution

Introduce a durable operation identity with a request fingerprint and unique constraint, scoped to a business event/version rather than assuming all lineage is globally one-to-one.

## Acceptance criteria

- [ ] Concurrent equivalent retries return one journal/result across HTTP, contract and Kafka paths.
- [ ] Same key with different financial content fails clearly.
- [ ] Reversal and legitimate multi-journal source events have distinct operation identities; no blanket lineage uniqueness breaks those flows.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

Existing sequential adapter reuse tests do not prove concurrent uniqueness or payload equality.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
