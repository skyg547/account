## Problem statement

The HTTP master OPEN/CLOSED update commits independently before local calendar, audit and approval records commit. A lost response or later local failure rolls back only local work.

## Reproduction / evidence

Static fault schedule: master commits OPEN during reopen, then response is lost or local calendar save fails. Local approval remains PENDING/calendar CLOSED, while Journal sees OPEN; a retry also encounters master no longer CLOSED. This is specific to remote deployment, not a claim about a shared local transaction.

Evidence level: source and call-path analysis. The described failure schedule is a reproduction plan unless explicitly identified as executed above.

## Financial / architectural impact

Posting can be enabled without a durably completed reopen approval, and close/reopen states diverge across services.

## Proposed solution

Use durable operation identity, expected-state transitions and recoverable orchestration; keep journal admission fenced until the authorized operation is durably finalized and reconciled.

## Acceptance criteria

- [ ] Inject failure after remote commit, before response and during each local save/commit.
- [ ] Recovery converges master/calendar/approval/audit state without silently opening an unapproved period.
- [ ] Retries identify the same operation and cannot replay a different transition.
- [ ] Add regression coverage that fails on the audited version and passes after remediation; preserve existing financial controls.

## Test gap and verification limits

HTTP response-validation tests do not simulate committed remote side effects followed by local rollback.

The six requested module suites passed 369 tests, but their success does not establish this missing control. No production data, live PostgreSQL, distributed fault injection or production load testing was used for this audit. A remediation must supply the relevant additional evidence before this issue is closed.
